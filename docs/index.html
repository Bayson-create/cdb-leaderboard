How much Safety, Comfort & handling and Operation does an automated-driving software stack keep when its LiDAR information is degraded in a controlled way? The bench drives every stack through the same seven traffic tasks, four registered severities and five repeats inside a CARLA · vEDGAR · Autoware loop, and scores what the vehicle actually did. Scores are degradation-robustness indices: S0-normalised retention of each endpoint, not absolute performance. One configuration, one map, one controller profile per entry. Read the methodology →

The benchWhat every entry is driven through

Registered intervention

Content range clip with thinning on the concatenated LiDAR cloud, applied post-capture to the perception consumer only (localisation keeps the nominal cloud). All points beyond a fixed 50 m planar range are removed, then every remaining point is kept with a seeded probability of 0.75 (S1), 0.50 (S2) or 0.25 (S3). S0 is the unmodified reference. The intervention is time-stamped (requested → applied → confirmed) on the simulation clock and verified per run.

Matrix and acceptance

7 scenarios × 4 severities × 5 unique accepted repeats = 140 runs, 28 of 28 cells. A run enters the matrix only after the data gate accepts it: intervention records complete, sensor cadence unchanged, required stage and vehicle records present, derived files hash-verified. Rejected attempts are retained as exclusions and never fill a slot.

Fixed environment

CARLA 0.9.16 · Town10HD · fixed Δt 0.05 s · scenario seed 20260805 · vEDGAR 1.0.3 vehicle and bridge · Autoware (TUM tum_launch) with NDT/EKF localisation · baseline MPC controller. Only the perception model / stack build differs between entries.

Seven traffic tasks

Stopped lead · Slow lead · Urban curve · Occluded pedestrian · Cross traffic (ego signal forced green — a conflict test, not a compliance test) · Construction obstacle · Dynamic cut-in. Each task consumes spatial observation differently, which is why the index is reported per scenario before it is averaged.
