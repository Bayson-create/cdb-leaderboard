Submit results

Any team can run its own perception model or stack build through the bench and appear on the leaderboard. The pipeline, matrix contract and scorer are the same ones that produced the reference entry; nothing is re-scored by hand.

Entries are accepted only as a complete 7 × 4 × 5 matrix that passes the validator. Partial matrices, extra repeats replacing rejected runs, or edited metric files are refused — the validator checks cell completeness, intervention timestamps and metric schema, and the build re-computes every number from run-level values.

1 · Plug in your model

Three integration points exist in the reference pipeline (ma-xie_vedgar_perception_degradation):

Swap a detector shipped with the stackSet lidar_detection_model in config/tum_launch/env (centerpoint, centerpoint_tiny, transfusion, pointpainting, bevfusion_lidar, bevfusion_camera_lidar) and model_path to your tum_models checkout.
Camera–LiDAR fusionrun_full_pipeline.sh --perception-profile camera_lidar mounts the 8-class fusion parameter set and engine and records perception_profile.json.
Bring your own detectorSubscribe to the degraded cloud on /sensing/lidar/degraded/pointcloud (the --perception-input-topic) and publish autoware_perception_msgs/DetectedObjects on /perception/object_recognition/objects. Everything downstream — validation, tracking, prediction, planning, control — stays the reference build so that the entry remains comparable.

Keep --controller-profile baseline unless the entry is explicitly a controller comparison; a different profile is a different entry.

2 · Run the matrix

python3 scripts/generate_supplementary_schedule.py --out formal_schedule.json --seed 20260902 --intervention content
python3 scripts/run_supplementary_campaign.py \
  --schedule formal_schedule.json --repo-dir . \
  --recordings-root ~/recordings/cdb_<entry> --raw-root ~/raw/cdb_<entry> \
  --registry registry.csv --exclusions exclusions.jsonl \
  --intervention content --smoke-approval --storage-budget storage_budget.json \
  --missing-only --execute --frame-conversion-verified

Each accepted run directory contains manifest.yaml, file_hashes.sha256 and metrics/full_metrics.json. Runs that fail the data gate are logged in exclusions.jsonl and the campaign re-attempts the slot (max 2 attempts) — it never promotes a rejected run.

3 · Package

A submission is one package.json:

{
  "schema": "cdb-submission/1.0",
  "entry": {"id": "<org>_<detector>_<controller>", "model": "…", "creator": "…",
            "detector": "…", "fusion_mode": "lidar|camera_lidar_fusion",
            "controller_profile": "baseline", "stack_version": "…", "commit": "…"},
  "runs": [ {"run_id": "…", "scenario": "lead-slow", "severity": "S2", "repeat": 3,
             "metrics": { …subset of metrics/full_metrics.json… }, "source_sha256": "…"}, … 140 ],
  "provenance": {"evidence_snapshot": "…", "hashes_verified": "n/n", "generated_at_utc": "…"}
}

python -m cdb_score demo-package template.json writes an empty template; cdb_score/spec.py::PACKAGE_METRIC_KEYS lists the keys to copy. Scenario slugs: lead-stopped, lead-slow, curved-urban-road, pedestrian-emerge, red-light-violator, construction-obstacle, dynamic-cut-in.

4 · Validate & score locally

The current score specification is cdb-score/1.1: Safety 4 metrics, Comfort & handling 9 metrics (including MRM / hard / severe braking), Operation 4 metrics.

python -m cdb_score validate submissions/<entry-id>      # PASS / FAIL with per-cell counts
python -m cdb_score score    submissions/<entry-id>      # indices + 95 % intervals + per-scenario axes

The validator output you will see for a complete matrix:

{"status": "PASS", "n_runs": 140, "n_cells_complete": 28, "n_cells_total": 28, "errors": [], "warnings": [ … ]}

5 · Submit

  1. Add submissions/<entry-id>/package.json and an entry with "status": "real" to registry/models.json.
  2. Open a pull request. CI runs validate, build and the unit tests; the leaderboard is regenerated from your run-level values.
  3. Keep the raw run directories (rosbags, camera sidecars, CARLA ground truth) for one year so that an audit can re-derive full_metrics.json from source.

Access to the reference stack

The reference images (autoware/microservice/mono:cuda-humble-x86_64-0.3.8, carla-ros2-release:tum_0.9.16_v2, vEDGAR 1.0.3) and the tum_models weights are hosted on the TUM LRZ GitLab registry and currently require an account there. A public, redistributable image set is the main open item before external submissions can be accepted at scale; until then, contact the maintainer to arrange access or a run on the reference machines.
